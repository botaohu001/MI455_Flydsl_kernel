## 8.0 读之前必须知道的四件事

**① 这一轮测的是哪个 kernel。** v3–v5 跑在**原生 NN 流水线之前**的那套实现上：
NT 前向内核（fwd 与 dgrad 共用）+ 一个独立的 TN wgrad 内核，选型函数是
`_pick_config` / `_pick_tn_config`。本仓库交付的 kernel 是在这之上做的原生 NN
改造。凡是两者会分叉的地方（最主要是 `tile_n=192`，见 §8.4），本篇明确标出。

**② 交付表口径。** 24 个 MoE 行 × 3 pass = 72 点。HIP event 框住**完整 Python
调用**，一次重复 = `_time(iters=30, reps=5)`，**每点 10 次独立重复取中位数**，
`MFU = TF/s ÷ 5040`。时钟**未锁频**，逐点采 `sclk`。

> ⚠️ 这 24 行里的两个 Qwen3 用的是 Primus-Turbo `config.py` 的 shape
> （`moe_int` 被当成了 `hidden_size`：768→2048、1536→4096），**与 HF
> `config.json` 真值不符**。这是当时明确要求的口径，但那些绝对数字不能当作这两个
> 模型的真实性能，也不能与 HF 口径的表混比。GPT-OSS-20B 与 DeepSeek-V3 是真值。

**③ 每一轮的噪声底不同，脱离它读倍数没有意义。**

| 轮次 | 总收益（72 点 geomean） | 口径 | 噪声底 | sclk |
|---|---|---|---|---|
| **v3** | **1.1173×**（中位 1.0202×，最大 1.8477×，0 回退） | 同会话背靠背，相隔 62 秒，单向 | 未单独量；10 次重复 cv 0.02–0.38% | 1366–1400 MHz（DPM 退化档，见 §9.9） |
| **v4** | 1.0013×（**落在噪声底内**） | 夹心（v3→v4→v4→v3） | **±0.13%**（69 个对照点读到 0.9987×） | 1602–2150 MHz，中位 1816 |
| **v5** | **1.0151×**（48 个 NT 点 1.0225×） | 夹心（v4→v5→v5→v4） | **0.06%**（24 个对照点读到 1.0006×） | 1636–2147 MHz，中位 1814 |

噪声底怎么量出来的、为什么必须用夹心，见
[`09-measurement-methodology.md`](09-measurement-methodology.md) §9.1–9.2。

**④ 原始报告与 jsonl 不在本仓库内。** 本篇所有数字是从那批报告逐条核对抄过来
的，标注了出处小节，但一手证据（`perf_24cfg_v*.jsonl` 等）留在当时的工作目录，
没有随仓库发布。这点与 [`source-reports/`](source-reports/) 不同，读的时候请知道
证据链在这里断了一环。

## 8.1 宿主侧：把 47 µs 的 jit 派发换成 3 µs 的预绑定 launch

**[实测]** 收益最"便宜"的一条，而且它是后面所有 tile 实验的**前提**。

### 做了什么

给 NT 和 TN 各加一个 `_nt_launch` / `_tn_launch`，调用点由
`_launch_xxx(*args)` 改成走缓存好的 `CompiledFunction`；缓存 key 取
**constexpr 尾部**。

### 机理

`JitFunction.__call__` 每次调用都要重做六件与指针无关的事：对 29 个参数做
`inspect.Signature.bind`、`apply_defaults`、捕获全局量的漂移检查、compile-hint
解析、**把全部 29 个参数哈希成一个完整 cache key**、以及 compile/runtime 配对
检查。`flyc.compile()` 把这条路走一遍，然后交出它最终落到的 `CallState` ——
后者只做"填 ctypes 槽位 + 调用"。

**为什么 constexpr 尾部这个 key 是对的**（核对过 flydsl 源码
`jit_function.py:1296-1312`，不是推测）：`_resolve_and_make_cache_key` 对
Constexpr 参数取**值**，对其余参数取 `jit_arg.cache_signature()` 即**类型**。
所以 flydsl 自己的 key 里，指针 / 标量 / stream 的**取值根本不参与**；constexpr
尾部就是 artifact 的完整身份。

### 实测收益

宿主侧逐段（200 次中位）：

| 阶段 | 前 | 后 |
|---|---|---|
| **jit 派发** | **46.4 – 47.0 µs** | **3.0 – 3.1 µs** |
| `build_m_tile_map` | 20.7–21.0 µs | 20.7–21.3 µs（未动） |
| **wrapper CPU 合计** | **95.0 – 96.6 µs** | **32.6 – 33.2 µs** |

单改动消融（72 点，其余两条关掉）：**geomean 1.0294×，中位 1.0114×，最大
1.3515×，7/72 点 >+3%，零回退**。收益最大的点是 GPT-OSS Down `avg_m=512`
dgrad（1.351×）与 fwd（1.341×）。

交付表外还有一个更大的：HF 真值的 Qwen3-30B Down @ `avg_m=512`
（`N=2048, K=768`）fwd 从 **244.6 → 461.6 TF/s（1.89×）**，而**前后用的是同一个
tile config** —— 这 1.89× 是纯粹的宿主开销消除。

### 适用边界

- **收益只出现在宿主暴露的点上。** 96 µs 的 wrapper 是**异步下发**的，与上一个
  内核的执行重叠，只有超出 GPU 时间的那部分才暴露。graph 实测：优化前 72 点里
  真正被宿主拖住的只有 **4 个**，最大暴露量 **26.2 µs**（不是 96 µs）。用
  "µs/call < 3× 96 µs 地板"这种启发式会把 37/72 判成 host-bound，其中 **31 个是
  误报**（详见 §9.5）。
- **已知且有意接受的差别**：flydsl 每次调用会重读 `_env_` 前缀的环境变量，我们的
  缓存不会。进程中途改 flydsl 环境变量会让它失效而我们不会。
- 本仓库的 kernel 已经带这条（`_nt_launch` + `_NT_COMPILED`、`_vk_launch` +
  `_VK_COMPILED`）。

## 8.2 wgrad 的 tile 规则：那个小 `avg_m` 分支根本不该存在

**[实测]** v3 三条改动里单项收益最大的一条（geomean 1.0596×）。

### 做了什么

`_pick_tn_config` 里删掉 `if avg_m <= 512: return (64,64,64,2,2,2)`，换成只在
`N < 256 or K < 256` 时才回退小 tile（描述符回退需要有一整个 tile 可退）：

```python
# 之前
if avg_m <= 512:
    return (64, 64, 64, 2, 2, 2)
return (256, 256, 128, 4, 2, 2)

# 现在
if N < 256 or K < 256:
    return (64, 64, 64, 2, 2, 2)
return (256, 256, 128, 4, 2, 2)
```

### 机理（这条比数字更该记住）

原来的规则**把前向的几何搬错了地方**。在 fwd 里 `avg_m` 是**输出维**，token 少
确实填不满高 tile。但 wgrad_tn 的输出是 `db[g]`，形状 `[N, K]`，**由权重决定，
与 `avg_m` 无关**；`avg_m` 在这里是**规约深度**。所以缩小 tile 一点 occupancy 都
换不到，只是把同一份 `db` 的输出流量放大了 —— 64×64 相比 256×256，在 FLOPs 完全
相同的前提下要把 `db` 足迹重载 **16 倍**。

### 实测收益

扫描（24 行 × 6 个候选 tile，行内交错，sclk 1394–1400 MHz）：
**256×256×128 在 12 个 `avg_m ≤ 512` 的行里赢了 11 个、平了 1 个**；旧的
64×64×64 在 12 行里有 **10 行垫底**。逐行比值 1.030× – **1.727×**。

单改动消融（72 点）：**geomean 1.0596×，中位 1.0019×，最大 1.7239×，11/72 点
>+3%（全部是 `wgrad_tn`），零回退**。`avg_m > 512` 的 12 行扫下来仍然是
256×256×128 最快，规则在那里不变。

### 适用边界

- **`avg_m=128` 只涨 3.0%–14.3%，因为那里已经不是 tile 的问题**：DeepSeek-V3
  wgrad 在 `avg_m=128` 时要为 240 GFLOP 写出 **1.88 GB** 的 `db`
  （`G×N×K×2` = 32×4096×7168×2），算术强度 **0.128 FLOP/byte**，是**输出带宽
  墙**。394 TF/s 对应 0.611 ms 写 1.88 GB ≈ 3.1 TB/s。换任何 tile 都救不了。
- 本仓库 `_pick_variable_k_config` 已经**刻意不看 `avg_m`**，并且记了同一条机理。
- ⚠️ 这条**不能**反向套到 fwd/dgrad：那里 `avg_m` 确实是输出维，小 tile 分支是
  必要的（§8.3）。

## 8.3 fwd/dgrad 的小 `avg_m` tile：一半是推导的，一半是拟合的

**[实测]** 单改动消融 geomean 1.0208×，中位 1.0023×，最大 1.3789×，13/72 点
>+3%。但这条规则内部**两个条件的证据强度完全不同，必须分开读**。

```python
if avg_m <= 64:
    return (64, 128, 64, 1, 4, 3)          # v3 未改、未测
if avg_m <= 128 or (n_groups and n_groups * ceil(avg_m/256) <= 8):
    return (128,128,128,2,4,2) if K % 128 == 0 else (128,128,64,2,4,3)
if K % 128 == 0:
    return (256, 256, 128, 4, 2, 2)
return (256, 256, 64, 4, 2, 3)
```

（warp 网格那两位后来被 §8.5 全部改成 `2,2`。）

### (a) `avg_m <= 128` —— 机理清楚，外推风险低

一个 256 行的 tile 在专家只有 128 个 token 时最多填一半。阈值从 `avg_m <= 256`
**下移**到 128：在 `avg_m=256` 上 256-tile 恰好填满且反超。同时把这一档的
`tile_k` 从 64/buf3 改成 128/buf2（`K % 128 == 0` 时）。

实测：DeepSeek-V3 四个 `avg_m=128` 点比 256-tile 快 **1.09×–1.36×**，比**原来
的** 64/buf3 快 **1.05×–1.09×**；四个 `avg_m=256` 点改用 256-tile 后
**1.06×–1.13×**。

### (b) `n_groups * ceil(avg_m/256) <= 8` —— ⚠️ 拟合的，机理只解释了一半

**触发范围极窄**：只在 gpt-oss（G=4）的 `avg_m=512` 上触发，**4 个点**
（两个 projection × 两个 pass），每个值 **1.34×–1.42×**。

**已证实的那一半（wave 量化）**：gpt-oss fc2 用 256-tile 时，`avg_m=512` 在 256
CU 上只有 **96 个 workgroup**，`avg_m=1024` 有 192 个 —— 两者耗时**同为 159 µs
和 162 µs**。不到一个 wave 时多干活是免费的，所以把 tile 减半拿到 368 个
workgroup 是唯一能换到东西的做法。这个模型也预测对了 `avg_m=1024/2048`
（宽 tile 赢 1.13×/1.09×，模型预测 1.13×/1.13×）。

**解释不了的那一半**：gpt-oss fc1 上 256-tile 已经有 184 个 workgroup，wave 量化
不适用。`[证据不足]`

**一条候选机理已被证伪**：`group_m`。8 个 M-tile 正好是 16 宽超级 tile 的一半，
看起来很像；实测在 {1,2,4,8,16} 上全扫，gpt-oss fc1@512 只动 **3.4%**、fc2@512
只动 **1.6%**，而 tile 值 **36–43%**。**不是它。**

### 适用边界

- 规则在 48 个交付点里有 **46 个**选中了实测最优 tile；让出的两个是
  **4.0%**（gpt-oss fc1 @ `avg_m=2048` fwd）和 **1.1%**（DSV3 fc2 @ `avg_m=256`
  fwd）。**这是有意的取舍**：把前者纳进窄 tile 分支，gpt-oss fc2 @1024 退
  12.2%–12.4%、@2048 退 8.1%–8.2%（实测）。
- **对 G ≤ 8 且 `avg_m` 在 256–512 之间的新形状，不要假设它是对的，扫一下再
  信**（样本只有 4 个点，机理只有一半）。

## 8.4 `tile_n = 192`：靠整除输出宽度拿的收益（⚠️ 拟合、机理未确立）

**[实测]** v4 唯一落地的改动。收益是实的，**门槛是拟合的**，而且它在本仓库的
原生 NN 路径上**用不了**。

### 做了什么

在 `tile_k=64` 分支前插一条：

```python
if avg_m >= 1536 and N % 192 == 0:
    return (128, 192, 64, 2, 4, 3)     # v5 之后是 (128, 192, 64, 2, 2, 3)
```

只有 `K=2880`（gpt-oss）会走到 `K % 128 != 0`，所以这条规则的作用域天然被限制
在 gpt-oss。

### 机理：两件事同时变了，扫描分不开

| | 旧 `256×256×64/b3` | 新 `128×192×64/b3` |
|---|---|---|
| N=5760 切块 | 23 块（22.5 真实，**半 tile**） | 30 块（**整除**） |
| N=2880 切块 | 12 块（11.25 真实，**1/4 tile**） | 15 块（**整除**） |
| LDS | 221184 B | **138240 B** |
| **WG/CU** | 1 | **2** |
| VGPR | 464 | **232** |

192 同时整除 5760(=30×192) 和 2880(=15×192)，而 256 两个都不整除。138240 B 是
这套 kernel 里**第一个跨过 `327680/2 = 163840` 这条线的生产配置** —— ragged 消失
和 occupancy 翻倍**同时发生，扫描无法分开**，v4 报告没有假装能分。

> 后来 v5 的归因阶梯把这两项拆开了，结论是**第二个 workgroup 才是值钱的那一半**
> （约 +15.5%），而**单独消除 ragged 是负的**（§8.5.3）。所以 v4 把 ragged 列为
> 主因之一属于过归因。

### 实测收益

| 口径 | 数值 |
|---|---|
| 交付表命中点（夹心，v4 噪声底 0.13%） | 行3 fwd **1.0676×**、行6 fwd **1.0635×**、行6 dgrad **1.0584×** |
| 两个测量方向的分歧 | **≤ 0.23%**，远在噪声底之上 —— 这三个点是实的 |
| 命中面 | **3 / 72** 点（`K%128!=0` ∧ `avg_m≥1536` ∧ `N%192==0`） |
| 扫描阶段读到的 | **+9 ~ 11%** |

> ⚠️ **口径不一致，需要更正一处**：`_pick_config` 的 docstring 引的是扫描阶段的
> "+9.0% / +10.7% / +10.3%"。全量夹心协议下是 **+6.8% / +6.4% / +5.8%**。
> v4 报告自己写明"以全量协议为准"。下次改那段 docstring 时应该换成后者。

### ⚠️ `avg_m ≥ 1536` 这个门槛：机理至今没找到

两次独立探测（3 轮 / 5 轮，行内交错）给出 `n192` 相对 `256×256×64/b3` 的增益：

| avg_m | 896 | **1024** | 1152 | 1280 | 1408 | 1536 | 1664 | 2048 | 3072 | 4096 |
|---|---|---|---|---|---|---|---|---|---|---|
| N=5760 | +5.4 | **−4.7** | −6.6 | +11.5 | +8.9 | +2.4 | +1.2 | +7.4 | +0.6 | +2.4 |
| N=2880 | +4.8 | **−13.7** | +23.5 | +20.3 | +16.0 | +11.7 | +8.9 | +5.2 | +9.4 | +10.8 |

`avg_m = 1024` 是一个**可复现的反转点**：两次探测、两个 shape、v5 在 4 波下重测
**依然复现**（0.923 / 0.840），所以它也不是 8 波网格的产物。

**排除掉的候选机理**（都是确定的负结果，不是未检验的猜测）：

1. **occupancy / 每 lane 寄存器**：26 个 `avg_m` 点上宽 tile 的 `wg_per_cu`
   **恒为 1**、窄 tile **恒为 2**，VGPR 不变。**一个常数不可能解释一个变量。**
2. **M-tile 量化废料**：`avg_m=1280` 对 BM=256 恰好整除、无废料，仍然只赢 1.111；
   `avg_m=1152` 有 10% 废料却在 fc2 上是全表最高的 1.192，**方向相反**。
3. **HBM 字节比例**：按字节算 `avg_m=1152` 应当 ≈0.71，实测 1.192，**差 68%**。

**仍然没有解释的**：宽 tile 吞吐在 `avg_m` 上有一个**可复现的锯齿**
（fc2 上 1024/1152/1280/1408/1536 处 980/737/802/868/924 TF/s，v5 重测为
1011/758/816/884/952 TF/s，**形状完全一致**），峰值恰好落在窄 tile 失手的地方。
反转点位置**与 shape 有关**（fc1 在 1024 和 1152 两点都 <1，fc2 只在 1024 一点
<1），所以它也不是一个纯 `avg_m` 现象。

**门槛就定在"排序被实测为稳定"的那段区间，刻意不外推穿过反转点。** v5 的重测
显示 4 波下 `128×192` 在 `avg_m ∈ {512,640,768,896,1280,1408}` 上也赢
（1.01–1.17×），所以 1536 现在是**偏保守的**；但没有动它，理由是
(a) 放宽不改变交付表任何一点；(b) 机理未知时把门槛推过反转点是没有依据的拟合。

### 适用边界（最重要的一段）

- **本仓库的原生 NN 路径用不了这个 tile。** 转置 B stage 的 LDS 行宽
  `tile_n*2` 就是 TDM 的 `pad_interval`，硬件要求它是 2 的幂，flydsl 报
  `padInterval must be a power of two (in elements), got 384`。所以
  `_pick_config_nn` 把 192 摘掉了，代价是原生 vs hoist 最差的那个点
  （gpt-oss fc2 dgrad @ avg_m=2048，**0.872**）。详见
  [`05-optimization-log.md`](05-optimization-log.md) §5.2 与
  [`06-pitfalls.md`](06-pitfalls.md) §6.2。
- **wgrad 上同样物理不可能**，原因同上。
- 这条规则**只在 `N % 192 == 0` 且 `K % 128 != 0` 时才有意义**，在本项目里等价于
  "只对 gpt-oss"。换一个 N 就要重扫。

## 8.5 ⭐ warp 网格 8 波 → 4 波（2×2）：最普适的一条

**[实测]** 259 组成对对照 geomean **1.0367×**。它只改 `mw × nw`，
**tile 尺寸、`tile_k`、`num_buffers`、LDS、ragged 行为、WG/CU 一个都不动**。

这一条推翻了一个听起来很有道理的假设。当时的猜测是：wave32 每 lane 要
`warp_tile_m × warp_tile_n / 32` 个 f32 累加器（wave64 的两倍），所以
`BM256/BN256` 对 wave32 **寄存器过载**，`tile_n=192` 的胜利主因是每 lane 累加器
从 256 降到 96。**实测方向完全相反**：

| | v4 生产几何 | v5 落地几何 | |
|---|---|---|---|
| 每 lane 累加器 | 256 | **512** | ↑ 2× |
| VGPR | 462 | **790** | ↑ 1.7× |
| 每 CU 波数 | 8 | **4** | ↓ 一半 |

**降低每 lane 累加器是错的方向；提高它、同时把 workgroup 的波数从 8 砍到 4，
才是 wave32 上的正确方向。**

### 8.5.1 主结果

只取重复间极差 < 5% 的干净点，同会话行内交错：

| tile | 翻转 | n | geomean | min | max | <1.000 |
|---|---|---|---|---|---|---|
| `256×256×128/nb2` | 8w(4×2) → **4w(2×2)** | 13 | 1.0132× | 0.994 | 1.037 | 1 |

### 8.5.3 归因拆解：`tile_n=192` 的胜利到底来自哪

15 臂 × (行3/行6) × (fwd/dgrad)，行内交错 5 轮，每臂只动一个因素，其余
（面积 / acc / LDS / ragged / 波数 / WG-per-CU）按标注固定。n = 4：

| 臂 | 只改了什么 | geomean | 范围 |
|---|---|---|---|
| **v4 的整体改动** | 四件事同时改 | **1.0715×** | 1.064 – 1.079 |
| **8 → 4 波** | `128×192×64` 的 `2×4 → 2×2` | **1.0244×** | 1.013 – 1.038 |
| warp 网格 | `256×256×64` 的 `4×2 → 2×4`（acc/LDS/ragged/W 全同） | 0.9820× | 0.975 – 0.997 |
| warp 朝向 | 固定 block tile `128×192`，warp tile `64×48 → 32×96` | 0.9828× | 0.975 – 0.991 |
| **occupancy** | `nb3 → nb4`：LDS 138240→184320，**2 WG/CU → 1**，tile/warp tile/acc/vgpr(232) 全同 | **0.8659×** | 0.850 – 0.888 |
| **波数 vs 独立 workgroup** | `8 波 × 2 WG → 16 波 × 1 WG`：**同一 tile、同为 16 波/CU** | **0.7628×** | 0.741 – 0.783 |
| **block 形状** | `128×192 → 256×96`：warp tile 同 64×48、acc 同 96、W 同 8、同 2 WG/CU、两者都整除 5760 和 2880 | **0.8437×** | 0.790 – 0.890 |
| block 形状 | `128×192 → 192×128` | 0.8922× | 0.851 – 0.933 |
| 面积 | `128×192 → 128×128`，同为 2 WG/CU | 0.8214× | 0.784 – 0.856 |
| **ragged 消除（保持宽 tile）** | `256×256` → `256×192`（整除） | **0.9206×** | 0.880 – 0.976 |
| 同上 | → `192×192` | 0.9577× | 0.936 – 0.983 |
| 同上 | → `256×160` | 0.9440× | 0.922 – 0.960 |

四条结论：

**① 每 lane 累加器数不决定性能。** acc（96）、warp tile（64×48）、波数（8）、
WG/CU（2）全同、两者都 ragged-free 的 `128×192` 与 `256×96` 差了 **15.6%**。
更直接的反证是落地几何把 acc/lane 从 96/256 **提高**到 192/512，反而更快。

**② 单独消除 ragged 不值钱。** 三个"整除但保持宽 tile、仍 1 WG/CU"的候选
`256×192` / `192×192` / `256×160` **全部输给 ragged 的 `256×256`**。

**③ 第二个常驻 workgroup 值约 +15.5%。** `nb3 → nb4` 只把 LDS 从 138240 推到
184320（越过 163840），tile / warp tile / acc / vgpr(232，ISA 实测) 一字不差，
而 `nb4` 的预取流水**更深**（按流水线本身算它不该更慢），实测 0.8659×。
*（推断标注：`nb` 本身的影响没有在 `128×192` 上单独隔离，依据是 v4 在 `256×256`
上实测 `nb3` vs `nb4` 近中性。）*

**④ 起作用的是"独立的 workgroup 数"，不是"波数"。** `16 波 × 1 WG` 与
`8 波 × 2 WG` 在**同一个 tile 上、同为 16 波/CU**，前者只有后者的 **0.763×**。
机理：一个 workgroup 内部所有波被 barrier 锁在同一个流水相位；两个 workgroup
可以各处在 K 循环的不同位置，一个的 TDM DMA 盖住另一个的 WMMA。

**有一臂剥不开，如实说剥不开**：`256×256×64/mw4/nw2/nb2`（LDS 147456 < 163840，
LDS 允许 2 WG 而寄存器只允许 1）本来是"寄存器 vs LDS 谁是约束"的判决实验，实测
0.8169×，**但它同时把 `nb3` 降成了 `nb2`**，而同一轮里 `128×192` 的
`nb3→nb2`（WG/CU 不变）也损失 0.8181×。两者几乎相等 ⇒ 这一臂的损失可以被
`nb2` 单独解释完，**判决不成立**。

### 8.5.4 为什么十几轮扫描从没发现它

专门的 warp 网格扫描覆盖 `2×4 / 4×2 / 4×4 / 2×8 / 8×2` —— **每一个都是 8 波或
更多**；超过 8 波的都 spill，于是得出"不要追占用率"。**那次扫描里往下的方向一次
都没试。**

> ⚠️ **但 v5 报告里"往下一次都没试过"这句话需要更正。** 回查更早那轮
> `tile_k=128` 的 ISA 门，`256,256,128,**2,2**,2`（就是 4 波 2×2）**在里面**：
> 门是 PASS（vgpr **791**、spill 0），旁边写着 **"实测 −0.6%，弃"**。
>
> 也就是说这个几何被试过一次，**在一个形状上（deepseek fc1，G=8，`avg_m`=8192）
> 读到 −0.6% 就被丢掉了**。v5 对同一个 tile 的同一个翻转在 **47 个点**上读到
> **+1.3% ~ +1.5%**，在别的 tile 上最高 +5.3%。
>
> 所以准确的说法不是"没试过"，而是：**它被一次单形状、单条件的读数判死了。**
> 这条比"扫描盲区"更值得记 —— 见
> [`09-measurement-methodology.md`](09-measurement-methodology.md) §9.7 的最后
> 一条。

另一个真实的扫描盲区（候选菜单少喂了一半 tile）见
[`10-disproven-directions.md`](10-disproven-directions.md) §10.7③。

### 适用边界

- ⚠️ **不能搬到 variable-K（wgrad）。** TN 核上 `256×256×128` 的同一个翻转在 6 行
  上全是负的（**0.976 – 0.991**），所以 `_pick_tn_config` 保持 `mw4/nw2`。
  `128×128×128` 上这个翻转是 **+9.1% ~ +18.7%**（方向与 NT 一致），但
  `_pick_tn_config` 不会选 `128×128`（`256×256×128` 在 6 行上都更快 15%–30%），
  所以用不上。TN 的 `tile_m` 铺 N、`tile_n` 铺 K、`tile_k` 是 token 维归约，几何
  语义与 NT 不同，这**大概**是翻转在它的宽 tile 上失效的原因 —— **未验证**。
- 落地的六条分支全部 `spill = 0`，但**换 tile 就要重跑 ISA 门**：4 波把每 lane
  上限抬到 1024，很多候选是靠这个才过的。
- `avg_m ≤ 64` 那条分支（`64×128×64`）**没有交付形状命中，未测**。

## 8.6 两个把候选挡在 bench 之外的模型

这两个模型本身不产生加速，但它们**省掉的实验轮次比任何一条优化都多**。

### 8.6.1 wave32 的寄存器闭式模型与 VGPR 悬崖

**[实测 + 代数]** 源码给出的每 lane 用量：

```
n_acc      = (wtm/16) · (wtn/16)                 c_frags，每个 8 个 f32
acc/lane   = 8 · n_acc = wtm·wtn / 32
frag/lane  = 2 · (wtm/16 + wtn/16) · 8 = wtm+wtn  预取的 cur + nxt
vgpr/lane ≈ wtm·wtn/32 + wtm + wtn + c            c ≈ 14–24（实测）
```

在 workgroup 的 `W = mw·nw` 个波上求和，代入 `tm = mw·wtm`、`tn = nw·wtn`，
**warp 维度会消掉**：

> **regTot = tile_m·tile_n/32 + nw·tile_m + mw·tile_n + W·c ≤ 4096**

`4096 = 131072/32`，就是那条悬崖规律 **`VGPR 上限 = 131072 / flat_workgroup_size`**
改写成"求和的预算"。两条推论是**代数，不是假设**：

1. **累加器项里没有 warp 网格。** 一个 block tile 的累加器总占用只由它的**面积**
   决定，把同样的波重新排布在它上面不可能让总量变小。
2. **定 tile 面积时 `nw·tile_m + mw·tile_n ≥ 2√(tile_m·tile_n·W)` 随波数单调
   增**，而每 lane 上限 `4096/W` 减半的速度比累加器变小的速度快。

⇒ **"更多 wave × 更小 warp tile"在 wave32 上不可能缓解寄存器压力，只有缩小面积
可以。**

完整约束还要加一条硬上限：**`vgpr/lane ≤ min(4096/W, 1024)`**。往 2 波走会把
`256×256` 的 vgpr 精确钉在 **1024** 并 spill 4485 / 6304 —— 与 `4096/W` 预算
无关。

悬崖的逐档实测（同一 tile，只改 warp 网格）：

| warp 网格 | 线程 | wave | VGPR 上限 | 实测 |
|---|---|---|---|---|
| 4×2 / 2×4 | 256 | 8 | **512** | 生产 462，spill 0；一个 `tile_k=256` 的候选 vgpr 512 → **spill 791** |
| 4×4 | 512 | 16 | **256** | vgpr 256 → spill 552（另一轮同几何 spill 420） |
| 8×4 | 1024 | 32 | **128** | vgpr 128 → spill 512 |

分界很干净：**≤471 的全部 spill=0，=512 的全部 spill≥44**。

**模型的精度边界（如实标注）**：75 个 config 的 ISA 校验里，2 的幂 tile 上残差
`vgpr_isa − vgpr_model` 为 **−14 … +5**（≤3%，31 个点）；**含非 2 的幂维
（192/160/224/96）的 tile 上是 −14 … +238**（均值 +35.0，44 个点），主要发生在
`tile_n ∈ {160,192}` 配 `tile_k=128`。**低估的原因没有查**。低估意味着模型偏
乐观，所以实际的门用的是 **ISA 实测值**，模型只用来排候选。

### 8.6.2 `T_tile = F + n_phase × P` 与"固定成本其实是输出字节"

**[实测]** 固定 `N, G, avg_m` 和 tile 配置、只动 `K`，tile 数与 `K` 无关，所以
workgroup 波数 `W` 恒定：

```
t(K) = L + W × (F + n_phase × P),      n_phase = K / tile_k
```

是 `n_phase` 的一条直线。**只用同一 trace 的 wall 和形状已知的 tile 数，不需要
绝对时钟** —— 这是它能跨越时钟断层的原因。

拟合（6 个 shape，每个 6–7 个 K 点）：**R² = 0.99917 – 0.99988**，"固定成本"占
wall **5.20% – 16.75%**。

再把 6 个 shape 的截距对**输出字节** `G × avg_m × N × 2` 回归：

```
截距(µs) = 8.85 + 输出MB / 6.19        R² = 0.9886   （跨 11.8 MB – 537 MB）
```

- `8.85 µs` = 每次 kernel 的启动/收尾地板
- `6.19 MB/µs` = epilogue 那次 TDM store 的等效带宽

**独立验证**：同机实测纯写带宽 **7.27 / 10.55 / 11.51 MB/µs**（64/256/512 MB），
读+写 5.98 / 6.98 / 7.25。拟合出的 6.19 是纯写上限的 **54%–85%** —— 对一个 tile
粒度、跨 CU 竞争、还要和别的 CU 的 A/B 读抢总线的 strided store 来说是合理的。

`L` 与 `W×F` 的分离（同 shape 扫 `avg_m` 让 `W` 动）：DSV3 GateUP
`L = 13.35 µs, F = 4.126 µs`（R²=0.98906，W∈{1,2,4,8}）；Qwen3-235B GateUP
`L = 11.84 µs, F = 5.194 µs`（R²=0.99737，W∈{2,4,8,16}）—— **只做了 2 个
shape，证据强度中等**。

> **这个模型最大的价值是阻止了三件事。** 那 5–17% 的"固定成本"里绝大部分是
> **epilogue 必须写的输出字节 + 硬件启动地板，不是可以删掉的指令**。同步指令
> 削减、barrier 删除、ballot group-find 三条候选加起来也够不着截距的零头
> （详见 [`10-disproven-directions.md`](10-disproven-directions.md) §10.3）。

剩余空间账：

| 成分 | 占 wall | 可动性 |
|---|---|---|
| K 循环（斜率 `W×P×n_phase`） | 83%–95% | 内核内部 |
| epilogue 输出写（`输出MB / 6.19`） | 1.8%–10.7% | **不可动**，且已跑到纯写带宽的 54%–85% |
| 启动地板（8.85 µs/次） | 0.8%–23.2% | 只能靠**少发 kernel**（融合），不是改内核 |

> ⚠️ **"启动地板"这个词在不同轮次指的不是同一个量。** 这里的 **8.85 µs** 是 6 个
> shape 的截距对输出字节回归后的**常数项**。更早一轮在**删 M-tile 表之前**的内核
> 上，把 grid 固定在恰好一波再扫 K，测到"纯 launch"在 `n_k` 从 4 到 8 时几乎不动
> ⇒ **硬性 launch 地板 ≈ 48 µs**。两个数不矛盾，是两个定义（一个是跨 shape 回归
> 的截距，一个是单形状的绝对下限，且内核版本不同）。**引用时带上定义。**

### 8.6.3 兑现率：省下来的周期不等于拿到的时间

**[实测]** 这是把"指令数少了 X%"翻译成"快了多少"时必须乘的那个折扣，而它**远小
于 1**。两个独立测到的数：

| 场景 | 省了多少 | 实测拿到 | **兑现率** |
|---|---|---|---|
| `tile_k` 64→128（省的是真实发射工作） | 指令数 19752 → 15895（**−19.5%**）⇒ 反事实预测 **+24.3%** | **+10.7%** | **0.44** |
| TN 循环体地址外提（省的是停顿填充） | 循环体指令 560 → 330（**−41%**） | **+5.7%** | **0.14** |

**机理一（0.44）—— 功耗墙把省下的周期吃掉一半多。** 这颗卡在负载下**钉在功耗
cap**（`SOCKET_POWER` 2497–2503 W，`PPT_VIOLATION_ACTIVITY` **100%**），sclk 从空
载 2250 MHz 掉到 **1429–1466 MHz**。省下周期 ⇒ 功耗预算被同一个 kernel 更快地吃
掉 ⇒ DVFS 把时钟压回去。方法论文档给的经验值是 **≈0.45**，实测 **0.44**，
**两条独立途径吻合**。

**机理二（0.14）—— 删掉的是 `v_nop` / `s_wait*` 填充，不是发射工作。** 那 41% 的
指令里主体是等待和填充；**等待的根因（LDS 转置读的地址运算与依赖停顿）还在**，
删掉填充只是把同一段等待换了个写法。

**可操作的判据**：

- 看到 `v_nop` / `s_wait*` 占比高，**不要当成"可回收的周期"** —— 先问那些等待在等
  什么。
- 任何"指令数 −X% ⇒ 快 X%"的估算都要乘兑现率。在功耗墙上、且省的是真实发射工作
  时用 **~0.45**；如果省的是停顿填充，量级是 **~0.15**。
- 这一条与 §8.6.2 的模型配合使用：先用 `F` 判"够不够大"，再用兑现率判"能拿到
  多少"。ballot group-find 那条候选两道都没过（
  [`10-disproven-directions.md`](10-disproven-directions.md) §10.3）。

## 8.7 拟合规则清单：哪些能外推，哪些不能

沿用本仓库的证据级别约定。**"拟合"不是"不可信"，是"只在被测过的区间内可信"。**

| 规则 | 状态 | 外推风险 | 依据 |
|---|---|---|---|
| 2×2 warp 网格（4 波） | **derived** | 低 | 机理（§8.6.1 代数）+ 259 组成对对照 |
| `avg_m <= 128` → 128×128 | **derived** | 低 | 256 行的 tile 半空；4/4 点一致 |
| `tile_k = 128` when `K % 128 == 0` | **derived** | 低 | ISA 可数清，+6.0–10.4% |
| wgrad 不看 `avg_m` | **derived** | 低 | `avg_m` 是规约维；12 行 11 胜 1 平 |
| `n_groups·⌈avg_m/256⌉ ≤ 8` → 128×128 | **拟合** | **高** | 只在 4/48 个点触发，全是 gpt-oss G=4；机理只解释一半 |
| `avg_m ≥ 1536 ∧ N%192==0` → 128×192 | **拟合** | **最高** | **机理未确立**；1024 处有可复现反转，只排除了 occupancy / M-tile 量化 / HBM 字节三条 |

两条拟合规则都**刻意只覆盖排序被实测为稳定的区间**。要在新 shape 上放宽任何
一条，先重跑扫描 —— 两条都核对过，放宽会在宽 tile 获胜的地方付 8–12%。

## 8.8 调用方今天就能拿到的：`m_tiles=` 复用

**[实测]** 这一条不在 kernel 里，而是一个**已量化但刻意没有默认打开**的收益。

`build_m_tile_map` 剩下的约 20.8 µs 是 6 个微小 device op 的 torch 下发开销
（sub / add / floordiv / cumsum / cat / to），约 3.5 µs 一个，与 G 无关。把它用
现成的 `m_tiles=` 入参提到调用外：

| 形状 | 每次调用 | 预建 `m_tiles=` | 增益 |
|---|---|---|---|
| GPT-OSS Down m512 fwd | 57.0 µs | **41.4 µs** | **1.376×** |
| Qwen3-30B Down m512 fwd | 101.0 µs | **85.3 µs** | **1.184×** |
| DSV3 GateUP m128 fwd | 360.4 µs | **344.5 µs** | 1.046× |

（端到端一整层的量化见 `RESULTS.md` §30.3：小 M 最高 **−20.7%**。）

**为什么不默认开**：要默认生效就得在 wrapper 里做自动记忆化，key 只能取
`(weakref, data_ptr, _version, block_m, G)`。`check_prebuilt` 是**校验调用方的
明示声明**，自动记忆化是**替调用方假设**。如果有人绕过 torch 的版本计数直接往
`group_offs` 的显存里写（自定义 kernel、`.data` 赋值），就会静默拿到过期的
map —— **结果错、无报错、无 NaN**。在"正确性不能退"是硬约束的前提下这个赌不值。

> 这正是 [`06-pitfalls.md`](06-pitfalls.md) §6.3 里 `AdamW(fused=True)` 不 bump
> `param._version` 那个坑的同一类风险，只是换了一个被缓存的对象。真实 MoE 层的
> 四次调用本来就共享同一张表，所以**调用方显式传 `m_tiles=` 是零风险拿到这
> 1.05×–1.38× 的正确做法**。

## 8.9.1 ⭐ `split_bar`：把一个 sub-step 的 WMMA 搬进 barrier 的信号—等待窗口

**借鉴自 HipKittens gfx1250 GEMM 阶梯的 `08_gemm_split_bar` 档。**

### 做了什么

`kernel/grouped_gemm_bf16_kernel_mi455.py` 的 `split_bar` 旋钮（默认 0 = 出厂
行为）。把每个 K-tile 的**最后一个 sub-step 的 WMMA** 从"barrier 之前"挪到
**`s_barrier_signal` 与 `s_barrier_wait` 之间**。

> ⚠️ **名字有误导性：barrier 本来就是拆开的。** gfx1250 后端把 `gpu.barrier()`
> 直接降成一对 `s_barrier_signal -1` / `s_barrier_wait -1`，出厂 ISA 里这两条只
> 隔一条指令。**这个旋钮加的不是"拆"，是往已经存在的窗口里塞活。** 所以
> `hk_isa_gate.py` 的 `s_barrier_signal` / `s_barrier_wait` 两列**不会变**（实测
> 全部 5/5 或 4/4 不变，bare `s_barrier` 恒为 0）；能证明它生效的是
> `same_asm_as_control = False`，即指令**顺序**变了。

### 机理

这颗 kernel 的 wave 抵达 rendezvous 的时刻**结构性地不齐**：只有 wave 0 和
wave 1 发 TDM 描述符，其余的总是先到。先到的 wave 原本坐在 barrier 上干等，现在
它在等的同时还能发一个 sub-step 的矩阵指令。

合法性：搬过去的那条只读寄存器。它的 LDS 来源已经被循环体末尾的
`s_wait_dscnt(0)` 抽干，而 barrier 只约束 wave 之间的先后，对内存不作任何声明。

⚠️ **`_split_fence` 里的 `sched_barrier(0)` 是承重的，不是装饰。** 去掉它编译器
会把矩阵指令直接沉出窗口，**答案依然正确**，所以损失是静默的。

### 实测收益

夹心口径（两个方向各一次取几何平均），10 次独立重复取中位数，同会话背靠背，
噪声底由逐字节相同的 `control` 臂在同一批里测出：

| shape | tile | sandwich | 判断 |
|---|---|---|---|
| `qwen3-235b-a22b` fc1 G16 N8192 K4096 m2048 | `256×256×128` | **1.0474×** | 真收益 |
| `gpt-oss-20b` fc1 G4 N5760 K2880 m1024 | `256×256×64` | **1.0392×** | 真收益 |
| `qwen3-30b-a3b` fc1 G16 N4096 K2048 m2048 | `256×256×128` | **1.0387×** | 真收益 |
| `deepseek-v3` fc1 G32 N4096 K7168 m512 | `256×256×128` | **1.0243×** | 真收益 |
| `gpt-oss-20b` fc2 G4 N2880 K2880 m2048 | `128×192×64` | 0.9977× | **噪声** |
| `deepseek-v3` fc2 G32 N7168 K2048 m128 | `128×128×128` | 0.9974× | **噪声** |

两批分别的 geomean：`tile_k=128` 的四个 shape **1.0268×**（噪声底 0.158%，
最差单个 control 点 0.907%，7 个干净 control 点）；`tile_k=64` 的两个 shape
**1.0182×**（噪声底 0.127%，但只有 2 个干净 control 点，**尺子偏薄**）。

sclk：负载下 **1909 – 1979 MHz**，空载 2257 – 2276 MHz。这是 §8.6.3 的功耗墙行为
（负载把时钟压下来），**不是** §9.9 那个 1400 MHz 的 DPM 卡死 —— 两者差一个量级，
不要混为一谈。

### 适用边界：**`WG/CU == 1`**，12/12 完全分离

> ⚠️ **本节更正了上一轮自己写的边界。** 上一轮只有 fwd 的 6 个点，从中读出的是
> "分界线是 warp tile 面积（`tile_m = tile_n = 256`）"。补上 dgrad 的 6 个点之后，
> **那是个相关量，不是原因**：大 tile 吃更多 LDS ⇒ 每 CU 装不下第二个 workgroup。
> 真正的自变量是 **每 CU 的 workgroup 数**。

12 个实测点（fwd 6 + dgrad 6，各自同会话夹心口径，已剔除超区间的脏点）：

| pass | shape | tile | LDS arena | **WG/CU** | sandwich |
|---|---|---|---|---|---|
| nn | `qwen3-235b-a22b` fc1 | `256×256×128` | 278528 | **1** | **1.0624×** |
| nn | `qwen3-30b-a3b` fc1 | `256×256×128` | 278528 | **1** | **1.0617×** |
| nn | `deepseek-v3` fc1 | `256×256×128` | 278528 | **1** | **1.0615×** |
| nn | `gpt-oss-20b` fc1 | `256×256×128` | 278528 | **1** | **1.0503×** |
| nt | `qwen3-235b-a22b` fc1 | `256×256×128` | 278528 | **1** | **1.0474×** |
| nt | `gpt-oss-20b` fc1 | `256×256×64` | 221184 | **1** | **1.0392×** |
| nt | `qwen3-30b-a3b` fc1 | `256×256×128` | 278528 | **1** | **1.0387×** |
| nn | `gpt-oss-20b` fc2 | `256×256×64` | 215040 | **1** | **1.0264×** |
| nt | `deepseek-v3` fc1 | `256×256×128` | 278528 | **1** | **1.0243×** |

- **`WG/CU = 1`：9 个点，geomean 1.0457×，区间 1.0243 – 1.0624 —— 全赢。**
- **`WG/CU = 2`：3 个点，geomean 0.9926×，区间 0.9830 – 0.9977 —— 一个都没赢，
  且 dgrad 上那个是真负收益（−1.70%）。**

**两组完全不重叠**：最差的 WG/CU=1 点（1.0243）与最好的 WG/CU=2 点（0.9977）之间
隔着 2.7 个百分点。

### 机理（WG/CU 这条解释得了负收益，warp tile 那条解释不了）

这个旋钮回收的是**先到的 wave 干等在 barrier 上时白白空掉的发射槽**。

- **`WG/CU = 1`**：那些槽真的空着，没有别的 workgroup 能填 ⇒ 塞进去一个 sub-step
  的矩阵指令是净赚。
- **`WG/CU = 2`**：同驻的那个 workgroup **本来就在填这些槽**，没有东西可回收 ⇒
  只剩下 `_split_fence` 的开销（一个 `tensor_wait` 加几个 `sched_barrier`，外加
  signal/wait 附近的重排）⇒ **净亏**。

这就是为什么 dgrad 的 `deepseek-v3` fc2 不是"读不出"而是"**−1.70%**"。旧的
warp-tile 说法只能解释"没有收益"，解释不了"有损失"。

### 一个事前预测，事后被证实（这条比数字本身更值得记）

补 dgrad 之前，用旧边界（warp tile）和新边界（WG/CU）对 **`gpt-oss-20b` fc2**
这个点的预测**是分叉的**，因为它在两条路径上选到了不同的 tile：

| | fwd（NT） | dgrad（NN） |
|---|---|---|
| tile | `128×192×64` | `256×256×64` |
| LDS / WG/CU | 138240 / **2** | 215040 / **1** |
| 旧边界预测 | 读不出 | **赢**（是 256×256） |
| 新边界预测 | 读不出 | **赢**（WG/CU=1） |
| **实测** | 0.9977×（读不出） | **1.0264×（赢）** |

**同一个模型、同一层、同一份数据，只有 tile 变了，结论就翻了。** 两条边界在这里
都预测"赢"，所以这一点确认的是"边界不是 shape 属性"；把两者分开的是
`deepseek-v3` fc2 dgrad 的**负收益**（旧边界预测"读不出"，新边界预测"亏"，实测
**−1.70%**）。

### 其余边界

- 12 次编译门 **spill 全部为 0**，LDS 与 WMMA 条数与 control 完全一致。
- **判 `WG/CU` 要用重算的 arena，不要用 `.group_segment_fixed_size`** —— 后者在
  动态 `SharedAllocator` 下恒读 0（§9.4 陷阱 2）。`hk_isa_gate.py` 的
  `lds(calc)` 列就是重算值。
- ⚠️ 与 `half_n_skip` **不兼容**（代码里直接 raise）：被跳过的 wave 没有可延后的
  sub-step。`half_n_skip` 默认关且本身实测为负，所以这不是实际约束。
- **wgrad（TN）路径仍未测。**

### dgrad 上比 fwd 更值钱

|---|---|---|---|---|
| **dgrad（NN）** | **1.0405×** | 6 | 0.134%（16 个 control 点） | 1.438% |
| fwd（NT，`tile_k=128`） | 1.0268× | 4 | 0.158%（7 个 control 点） | 0.907% |
| fwd（NT，`tile_k=64`） | 1.0182× | 2 | 0.127%（2 个 control 点，**尺子薄**） | 0.323% |

**dgrad 上 6/6 都超过最差单个 control 点**，且这正是本 kernel 的价值核心路径
（README：原生 NN 流水线，不物化转置副本）。dgrad 的 skew 更大是合理的 —— B 要

## 8.9.2 `sched_style`：一个 sub-step 一批，收益小且不普适（⚠️ 假设被证伪，收益是副产品）

**借鉴自 HipKittens gfx1250 GEMM 阶梯的调度档。**

### 做了什么

用"每个 sub-step 一批、批与批之间用 `sched_barrier(0)` 隔开"替换出厂的
`sched_dsrd` / `sched_mfma` 细粒度 group-barrier 交织。

### ⚠️ 原假设是反的

原假设写在 `hk_isa_gate.py` 里：**这么改会减少每个 K-tile 的操作数流水线抽干次
数**。编译门实测**完全相反** —— `s_wait_dscnt` 每 K-tile：

| shape 族 | control | `sched_style=1` | 倍率 |
|---|---|---|---|
| `256×256×128`（三个 shape） | 8.50 | **13.00** | **1.53×** |
| `256×256×64`（gpt-oss fc1） | 2.33 | **8.00** | **3.43×** |
| 6 个 shape 平均 | 6.00 | **10.19** | **1.70×** |

**抽干次数涨了 1.5–3.4 倍，端到端却仍然略快。** 所以拿到的那点收益**不是原假设
说的那个机理**，真实机理未确立。vgpr 与 LDS 一点没动，指令数微降（2378 → 2352）。

### 实测收益

| shape | sandwich | 判断 |
|---|---|---|
| `gpt-oss-20b` fc1 | 1.0268× | 真收益 |
| `qwen3-235b-a22b` fc1 | 1.0138× | 真收益 |
| `deepseek-v3` fc1 | 1.0135× | 真收益 |
| `deepseek-v3` fc2 | 1.0077× | 真收益（勉强） |
| `gpt-oss-20b` fc2 | 1.0032× | **噪声** |
| `qwen3-30b-a3b` fc1 | 0.9966× | **噪声（微负）** |

geomean：`tile_k=128` 批 **1.0079×**（4 点中只有 2 点超过最差 control 点
0.907%）；`tile_k=64` 批 **1.0149×**（2 点，尺子薄）。

### dgrad（NN）上明显更强、也更一致

同一批 dgrad 测量（噪声底 0.134%，16 个 control 点，`--noise-dup 3`）：

| shape | NN tile | WG/CU | sandwich |
|---|---|---|---|
| `gpt-oss-20b` fc1 | `256×256×128` | 1 | **1.0284×** |
| `qwen3-235b-a22b` fc1 | `256×256×128` | 1 | **1.0280×** |
| `deepseek-v3` fc1 | `256×256×128` | 1 | **1.0239×** |
| `qwen3-30b-a3b` fc1 | `256×256×128` | 1 | **1.0221×** |
| `gpt-oss-20b` fc2 | `256×256×64` | 1 | **1.0181×** |
| `deepseek-v3` fc2 | `128×128×128` | **2** | 0.9984×（读不出） |

dgrad geomean **1.0180×（+1.80%）**，5 个 `WG/CU = 1` 的点**全部**超过最差单个
control 点，唯一读不出的又是 `WG/CU = 2` 那个 —— **与 `split_bar` 同一条边界**。

### 适用边界

- **fwd 上弱且不普适**（6 点里 2 个读不出、1 个微负，量级与最差 control 点相当），
  **dgrad 上是稳定的 +1.8%**。要用就在 dgrad 上用。
- 与 `split_bar` 同样受 **`WG/CU = 1`** 约束。
- ⚠️ **机理仍未确立**：原假设（减少操作数流水线抽干）在 dgrad 上同样被证伪 ——
  抽干从 8.00 涨到 11.50（1.44×），照样更快。**一个假设被证伪、数字却是正的，
  不能当成假设被证实。**
- 与 `split_bar` **叠加效果未测**（两者都动 K-tile 尾部的调度，不能假定正交）。

## 8.9.3 ⛔ `split_bar` + `sched_style` 叠加：数字很好，但**配置处于暂停状态**

> ⛔ **先读这一段再看数字。** 这个组合**当前被禁止编译与测量**，理由见
> [`10-disproven-directions.md`](10-disproven-directions.md) §10.5.3。
> 2026-09-15 跑完这批之后不久 GPU 进入不可用状态、需要重启整机。
> **归因未确立**（那次 A/B 正常跑完、正确性闸 20/20 全过、持久化日志零记录、
> 幸存 dmesg 副本时间戳与 boot 记录矛盾、当天机器重启 7 次、静态分析未发现越界），
> 但在排除之前**保守对待**。下面的数字是**事件之前**测出来的。

### 实测（dgrad，5 个 `WG/CU = 1` 的 shape，噪声底 0.173%，14 个 control 点）

| 变体 | geomean | n | 区间 |
|---|---|---|---|
| `sched_style` 单独 | 1.0246× | 4 | 1.0192 – 1.0285 |
| `split_bar` 单独 | 1.0538× | 5 | 1.0282 – 1.0632 |
| **两者叠加** | **1.0620×** | 5 | 1.0320 – 1.0778 |

sclk 1905 – 2001 MHz；正确性 20/20 通过、**biteq 20/20**、nan 0。

### 正交性判断：**次可加（sub-additive），不是正交**

若完全正交，叠加应当约等于两者之积：

$$1.0538 \times 1.0246 = 1.0797 \quad\text{（预测）}\qquad\text{实测 } 1.0620$$

**实测比正交预测低 1.64 个百分点**，且叠加相对 `split_bar` 单独只多拿
**+0.78%**，而 `sched_style` 单独值 **+2.46%** —— 即**叠加时 `sched_style` 只兑现
了它单独价值的约三分之一**。

这与两者的机理一致：**它们改的是同一段代码**。`sched_style` 把 K-tile 尾部换成
每 sub-step 一批的 `sched_barrier(0)` 围栏，而 `split_bar` 把最后那个 sub-step
**整个搬出这段序列**、挪进 barrier 窗口 —— 被搬走的那个 sub-step 正是
`sched_style` 本来要重排的对象之一，所以它的作用面被削掉一块。**不能假定正交，
实测也确实不正交。**

⚠️ 以上数字**未经复现**，且其所属那次运行之后发生了 §10.5.3 记录的事件。
**在暂停令解除前，不要把这条写进任何默认配置。**
