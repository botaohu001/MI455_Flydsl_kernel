## 5.1 已采用

### `K % 128 == 0` 时用 `tile_k = 128` —— 最大的单项收益

**+6.0 – 10.4%**，ISA 层面可数清，机制清楚。derived，外推风险低。fwd、dgrad、
wgrad 三个方向都适用。

做 shape 规划时值得知道：规则的结构是
`if K % 128 == 0: tile_k = 128 else: tile_k = 64`，这保证了只要 `K % 64 == 0`
就一定能过门槛。gpt-oss 的 `K = 2880` 不被 128 整除，退到 64 深的 tile。
**而同一层在 dgrad 方向上 `K = 5760 = 45 × 128`，反而整除** —— 所以同一层
前向用 `tile_k=64`、反向用 `tile_k=128` 是合理的，不是 bug。

### 2×2 warp 网格（4 waves）

**259 个配对点上几何均值 1.0367。** derived，机制清楚，风险低。注意它**不能**
搬到 wgrad —— 见下文。

### `GROUP_M = 16`，不是 gfx950 的 4

**比 4 快 0.8 – 2.0%**，而且在 deepseek fc1 上 **4 是 {1, 4, 8, 16} 里最差的**。
gfx950 用一个 weight-slab 大小的启发式在 8 和 4 之间挑；那个启发式**没有在这里
重测过**，所以与其凭空发明一个放大后的阈值，不如无条件钉死 16。在 NN 路径上
扫 `GROUP_M` 是一个待办项。

### `avg_m <= 128` → 128×128 tile

在全部四个 DeepSeek-V3 `avg_m=128` 点上比 256 的 tile 快 **1.09× – 1.36×**。
derived：`avg_m=128` 时 256 行的 tile 有一半是空的。

### wgrad 用 `m_warp = 4`（不是 NT kernel 的 2）

**NT 那个 4-wave 2×2 网格不能搬到 variable-K。** 翻成 `m_warp=2` 在试过的全部
六行上测得 **0.976 – 0.991**，所以 `m_warp=4, n_warp=2` 保留。24 个 wgrad 交付
点全部跑 `BM256/BN256/BK128/mw4/nw2/nb2`。

### wgrad 的 tile 选择刻意不看 `avg_m`

在 wgrad 里 `avg_m` 是**归约**维而不是输出维，所以缩小 tile 只会把输出流量放大
—— 放大 16 倍。**[实测]** 在 12 个 `avg_m ≤ 512` 的交付行上，`256×256×128`
这个 tile **赢 11 平 1**。

### 预绑定的 `CallState` launch 路径

以 constexpr 尾部为 key 缓存预绑定的 launch 状态，**消除了 47.2 µs 的每次调用
CPU 开销**。

### 在 kernel 内做 expert 搜索，取代 host 侧 tile 表

`build_m_tile_map` 取代了 host 侧构建的 per-tile 表，后者固定花费
**约 92 µs/call —— 在 avg_m=2048 时占墙钟时间的 50.3%。**

### 转置 B stage 的 LDS 行距残数 —— 值 6.5%

**[实测]，机制未确立。** 把 pad 从 16 扫到 160、步长 16，六个 shape，始终对着
同一个 tile 上的 NT：

| `LDS_B_ROW % 64` | 相对 NT |
|---|---|
| **== 32**（pad 32、96、160） | **0.986 – 0.990** |
| 其它（16、48、64、80、112） | 0.928 – 0.933 |

**6.5%，每个 shape 都复现。** 这是"原生 NN 流水线比 NT 贵 7%"和"贵 1%"之间的
全部差距。上游 wgrad 的默认值 `LDS_PAD = 16` 在这个朝向下恰好落在**错的**一侧，
所以 `_nn_b_pad()` 挑那个获胜同余类里最小的 pad（`tile_n ∈ {128, 256}` 时是
32）。

**没有确立的是为什么是 32 mod 64。** 一个 16 字节粒度、32 bank 的模型预测
pad=16 无冲突、pad=32 四路冲突 —— **正好相反**，所以那个模型对这条指令是错的。
因此规则按它本来的样子陈述：一个实测到的同余类；遇到新的 `tile_n` 就重算，
不外推。（pad 大到会让 LDS 占用率减半的那些 —— `tile_n=128` 时的
128/144/160 —— 又会掉下去；*那一部分*是可解释的，所以函数返回的是该类里最小的
那个。）

### `tile_k == 64` 且 `avg_m > 128` 时把 `tile_n` 从 128 拓宽到 256

**[实测]，机制未确立。** 54 个合成 cell，其归约长度强制 `tile_k=64`，始终对着
同一个 tile 上的 NT：

| `tile_n` | 原生/NT 几何均值 | 达到或超过持平的 cell |
|---|--:|---|
| 128 | 0.896 | 10/54 |
| **256** | **1.103** | **44/54** |

`tile_n=128` 配 `tile_k=128` 没问题（0.96–1.05），所以**坏的是组合，不是 tile
宽度**。`avg_m > 128` 这个 guard 也是实测的：`avg_m=128` 时窄 tile 本来就已经
持平（0.945–1.135），拓宽反而要付 0.67–0.85×。

在交付矩阵里只命中**一行**（gpt-oss fc2 dgrad @ avg_m=512，值 1.26×），
因为它要求归约长度不被 128 整除，而矩阵里只有 2880 满足。

### tiled Triton 转置 —— 作为 benchmark baseline 保留

已经不在 kernel 里了（原生 NN 流水线让它不再必要），但它本身站得住：
**比 `make_nn_weight_nt` 快 11.0× – 14.9×**，逐位一致，约 20 行。

| 实现 | 带宽 |
|---|--:|
| `b.transpose(1,2).contiguous()` | 1.07 – 1.39 TB/s |
| 同样字节数的普通 `torch` 拷贝 | 7.05 – 11.1 TB/s |
| **tiled Triton 转置** | **15.5 – 17.1 TB/s** |

HBM4 峰值约 19.6 TB/s：helper 在峰值的 6–7%，替代品在 ~82%。
**如果你卡在一颗没有转置读指令的芯片上，这仍然是正确的修法。**
见 `benchmarks/bench_transpose.py`。

## 5.2 实测后否决

### 转置权重缓存 —— **不要做这个**

原型能用：38 条断言，0 失败。它仍然不该上线。

| | |
|---|---|
| 显存 | EP=8 下 **qwen3-235b +141 GiB（占 HBM 32.6%）、deepseek-v3 +152 GiB（35.2%）** |
| 能做小吗？ | **不能。** 反向每个 micro-batch 只访问每层一次，有界缓存命中率约 0。构造上全有或全无。 |
| 转置变快后的收益 | 42 格几何均值 **+7%**（1.099 → 1.171），且只作用于 dgrad |
| `avg_m ≥ 1536` 时的收益 | **没有** —— 那 24 格全部 N\* < 1，转置在单次调用内已经回本 |
| **正确性** | **`AdamW(fused=True).step()` 不 bump `param._version`。** 以 `_version` 为 key 的缓存于是返回上一步的转置结果：**9.99e-02 相对误差**，无异常、无 NaN、梯度看起来合理。端到端复现过。 |

`p.data.copy_()` 和 `p.data.add_()` 同样静默。完整表格见
`docs/02-dgrad-problem.md` §2.3。基于 hook 的失效可以做安全，但那是 kernel
无法强制的框架契约，而且它 fail open。

### `global_load_tr16_b128` —— 实测能用，未采用

**[实测]** gfx1250 上可用，lane 语义与 LDS 版相同，而且在**非 16 字节对齐**的
跨步（9 和 12 个元素）下也能正确转置 —— 这是 LDS 版做不到的。它可以把 B 从
显存直送 VGPR，完全不过 LDS，任意 `N` 都行。

不采用是因为：原生 NN 流水线达到 hoist 口径的 0.979 之后只剩约 2% 空间，而代价
是确定的 —— 丢掉 TDM 异步流水、丢掉硬件 OOB clamp（ragged N 要手写 mask）、
B 的复用从 LDS 降到 L1/L2、外加 VGPR 压力（wgrad 在 `frag_pipeline=1` 时已经
因此 spill）。

**这是关于剩余空间的判断，不是一次针对它的否定实测。** 当初推动它的场景 ——
小 `avg_m` 的 memory-bound dgrad —— 恰恰是原生流水线已经达到或超过 hoist 口径
的地方（deepseek fc2 @128 = **1.031**，fc1 @128 = 0.978）。如果有人接手，
这就是下一个实验。细节见 `docs/03-isa-investigation.md` §路线 5。

### `num_xcd = 8` —— 保持 1

`amd-smi metric -c` 报告 **8 个 gfx 时钟域**（`gfx_0_clk` … `gfx_7_clk`），
配 256 CU 即每 XCD 32 CU，与 MI355X 的 8 个吻合。这是**证据而非证明** ——
时钟域数量不必然等于 XCD 数量。

实测 `num_xcd=8, xcd_band=32` 对默认值，交错测量，每侧两轮：

| 行 | op | xcd=1 | xcd=8 | 比值 | |
|---|---|--:|--:|--:|---|
| gpt-oss fc1 | fwd | 0.0782 | 0.0718 | **0.918** | 快 8.2% |
| gpt-oss fc1 | wgrad | 0.0689 | 0.0698 | 1.013 | 慢 |
| qwen3-30b fc1 | fwd | 0.1110 | 0.1096 | 0.988 | 快 1.2% |
| qwen3-30b fc1 | wgrad | 0.1068 | 0.1120 | **1.049** | 慢 4.9% |
| qwen3-235b fc1 | fwd | 1.1380 | 1.1248 | 0.989 | 快 1.2% |
| qwen3-235b fc1 | wgrad | 1.2697 | 1.2735 | 1.003 | 平 |
| deepseek-v3 fc1 | fwd | 0.2902 | 0.2906 | 1.001 | 平 |
| deepseek-v3 fc1 | wgrad | 0.4115 | 0.3974 | 0.966 | 快 3.4% |

**混合结果：fwd 小幅获益，wgrad 多数受损。不构成改默认值的理由。**
那个 +8.2% 的离群点落在最短的点上（0.078 ms），而且每侧只测两轮 ——
**是值得用完整 sweep 去确认的线索，不是结论。**

### `b_imm_walk` —— 无差异，于是保留更安全的写法

B 描述符只建一次、用 `imm_offset` 走归约轴，而不是每 k-tile 重建：
**0.985 vs 0.990 —— 噪声。** 于是保留已验证的每 k-tile 重建，不为零收益去换一个
更容易在 extent 上出错的写法。

### `tile_n = 192` —— 不可用，而且这要付一个交付点的代价

这不是选择。B stage 行宽 `tile_n*2` 就是 TDM 的 `pad_interval`，硬件要求它是
2 的幂；flydsl 报 `padInterval must be a power of two (in elements), got 384`。
所以原生 NN 路径根本用不了 192 的 tile，只能退回 256×256×64。

原生 vs hoist 最差的那个点（**gpt-oss fc2 dgrad @ avg_m=2048，0.872**）
全部原因就是它。值得注意让掉的是什么：192 那条规则是 `_pick_config` 自己的
docstring 标为 **fitted、机制未确立、"the highest extrapolation risk in this
function"** 的规则。让掉的 tile 本身就是猜出来的。

## 5.3 已证伪的方向 —— 不要再提

以下每一条都实现并测量过。全都让性能变差。

| 方向 | 实测 |
|---|---|
| host 侧构建索引表 | 孤立看更便宜（56 vs 92 µs），但**端到端 −31%** —— D2H 同步杀死了调用间的重叠 |
| `inkernel_scan`（per-workgroup 前缀扫描） | 正确，但 **fwd −15.2% / dgrad −53.8%** |
| `half_n_skip`（跳过死列） | 在全部四个 gpt-oss 点上 **−1.3 到 −1.7%** —— TDM 本来就没去取那些列 |
| 更多 wave / 更高 occupancy | 16 wave × 1 WG vs 8 × 2 WG，同 tile：**0.763×** |
| 每 CU 2 个 workgroup 共驻 | **−7.0%** |
| 用 padding 消除 raggedness | 3 个正好整除的宽 tile 全都输给 ragged 的 256×256（**0.921 / 0.958 / 0.944**） |
| 用 device fp64 matmul 做数值参考 | **12 次错 11 次。** 参考必须是 fp32，在 host 侧判定。 |
| dgrad 拆成每组一次 `G=1` 的 variable-K 调用（改为转置激活） | 逐位正确，**慢 1.5× – 10.5×** |

关于 `amdgpu-expert-scheduling-mode`：这里所有 kernel 都开着它，所有正确性门也
都是在它开着的情况下过的。但类似的 Triton pass 曾被发现在这颗芯片上
**静默误编译** bf16 grouped GEMM，所以它是**被这些门验证的，而不是由构造保证
的**。改动它就要重新核对数值。

## 5.4 被证伪的假设（关于*为什么*）

听起来对、但实际不成立的解释。它们和优化本身一样有价值 —— 能让下一个人不必在
同一个故事上花掉一天。

### wave quantization **不能**解释小 `avg_m` 的失分

kernel "launches one workgroup per output tile with no persistent loop"，
所以一个刚过 wave 边界的 tile 数应该要付一整个 wave 的代价。拿 flydsl 的 GEMM
输给 Triton 的那些 cell 来检验：

**Spearman(wave efficiency, speedup) = −0.55 —— 符号反了** —— 而且**五个失分
cell 里有四个的 wave efficiency 恰好是 1.00**。不是这个机制。
见 `results/dgrad_study/wave_quant.txt`。

**小 `avg_m` 失分的真实原因至今未知。** 它早于 NN 工作，也未被它改变，
是本仓库里最有价值的开放问题。

### `N*` **不能**由 权重字节数 / GEMM FLOP 预测

这个判据死于代数：

```
权重字节 / GEMM FLOP = (G·N·K·2) / (2·G·avg_m·N·K) = 1 / avg_m
```

恒等 —— 与 G、N、K 全都无关。数值验证过：24 个 cell 全部
`ratio × avg_m == 1.0`。deepseek-v3 只是*看起来*更差，因为研究给它的是
`avg_m ∈ {128,256,512}` 而 gpt-oss 拿到的是 `{512,1024,2048}`；在相同 `avg_m`
下两者比值相同。

而且它不能给 `N*` 排序：Spearman = 0.744，但在 `ratio = 1.95e-03`
（`avg_m = 512`）这一个取值上 `N*` 横跨 5.27 到 ∞。因为

```
N* = 2 / ( BW_transpose · avg_m · (1/T_triton − 1/T_flydsl) )
```

—— `1/avg_m` 那部分就是这个比值，而吞吐差那部分不是，真正起决定作用的是吞吐
差。Spearman(flydsl/Triton 加速比, N\*) = **−0.827**，比那个比值更强。

这个比值*确实*干净地给出的东西是：**缓存的价值**（`t_transpose / t_gemm`）
正比于 `1/avg_m` —— `avg_m=128` 时 0.73–0.80，512 时 0.21–0.35，
2048 时 0.09–0.12。

### occupancy **不能**解释 `_pick_config` 里的 1536 阈值

这是一个已确认的否定结论，不是未经检验的猜测。在 26 个 `avg_m` 点上，宽 tile
**始终**是 `wg_per_cu = 1`、窄 tile **始终**是 2，VGPR 不变。两者都不是
`avg_m` 的函数，所以都不可能在某一个点上造成反转。M-tile 量化浪费也被排除
（`avg_m=1280` 完全没有浪费却仍然输；`avg_m=1152` 有 10% 浪费却是表里最好的
点，1.192）。一个 HBM 字节模型在 `avg_m=1152` 预测 0.71，实测 1.192 ——
偏差 68%。

仍然无法解释的是宽 tile 吞吐里一个**可复现的锯齿**（fc2 上 `avg_m` 取
1024 / 1152 / 1280 / 1408 / 1536 时为 980 / 737 / 802 / 868 / 924 TF/s），
其峰值恰好落在窄 tile 失手的地方。

### 转置摊销的线性模型恰好在你需要它的地方失效

`t_eff(N) = t_gemm + t_transpose/N` 在**慢转置**下误差中位仅 0.92%，
在**快转置**下于 **N = 1 处失效，最大 +35%** —— 一个固定约 5 µs 的 launch
边界，在 N ≥ 4 时不可见。而 N = 1 就是 per-call 那种情形，也就是这个模型正被
用来做的那个判断。细节见 `docs/02-dgrad-problem.md` §2.5。

### 寄存器压力**不能**解释原生 NN 流水线的 2.1%

用生成的汇编而不是假设来回答：VGPR 790 vs 791，两侧零 spill，两侧零 scratch，
WMMA 与 LDS 读计数相同，而且原生路径**少发 77 条指令**。剩下的只能是转置读的
单指令代价。表格见 `docs/04-native-nn-pipeline.md` §4.5。

## 5.5 开放线索，按值得尝试的顺序

1. **flydsl 的 GEMM 为什么在小 `avg_m` 输给 Triton？** 24 个 dgrad 格里有 4 个，
   无解释，wave quantization 已排除。这里最大的开放问题。
2. **把 `global_load_tr16_b128` 做成第二个 NN 变体** —— 约 2% 的空间，代价确定，
   从未在真实 GEMM 里测过。
3. **确认 MI455X 的 XCD 数量后做完整 `num_xcd` sweep。** 目前的证据是 8 个时钟
   域，加上最短点上一个 8.2% 的离群值。
4. **`b_pad` mod-64 规则的机制。** 它值 6.5%，而显而易见的 bank 模型预测相反，
   说明 LDS 交叉开关上有什么东西没被理解。
5. **在 NN 路径上扫 `GROUP_M`。** 现在钉在 16 是根据前向的测量，从未为 dgrad
   重测。
6. **root-cause gpt-oss fc2 的首调用损坏。** 这里没有复现，但"没复现"不等于
   "已修复"。目前靠 warm-up 约定盖过去。
