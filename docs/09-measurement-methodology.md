# 9. 测量方法论 —— 怎么让一个 +2% 站得住

[`08-tuning-playbook.md`](08-tuning-playbook.md) 里最值钱的一条优化是 **+3.7%**。
在一台**不锁频**、逐点 sclk 在 1600–2150 MHz 之间浮动的机器上，这个量级和噪声
只隔一层。本篇是那层东西：**先建尺子，再量长度。**

这些手段的可复用性高于任何单条优化 —— 换芯片、换 kernel、换 DSL 都还成立。

---

## 9.1 先量噪声底：一个必须读到 1.0000× 的对照组

**做法**：把交付表拆成两部分 —— 规则改动能命中的点，和**命中不了的点**。后者在
两个变体里跑的是**逐字节相同的代码**，所以它们的**真值必须是 1.0000×**。它们读
出来的偏差就是这次会话的噪声底。

三轮的实测：

| 轮次 | 对照点数 | 对照组读数 | ⇒ 噪声底 | 同批的"收益" |
|---|---|---|---|---|
| v4 | 69（72 点里规则只命中 3 个） | **0.9987×**（0.9863 – 1.0066） | **±0.13%** | 72 点 1.0013× ⇒ **测不出** |
| v5 | 24（`_pick_tn_config` 本轮未改） | **1.0006×**（0.9971 – 1.0039） | **0.06%** | 72 点 1.0151× ⇒ 信噪比 ~25× |

**这把尺子是判负的依据，不是装饰。** v4 有一条 `num_buffers` 3→4 的候选，第一次
扫描在行 2 fwd 上读到 **+2.46%**；加密探测同一个点读到 **−0.9%**，16 个 `avg_m`
点上 ±1.2% 随机分布、geomean ≈ +0.2%。**没有噪声底就会把它当成一条真收益写进
规则。**

反过来，v5 的 +2.46% 量级的数字是可信的 —— 因为同一批数据里的对照组读到了
1.0006×。**同一个数字在 v4 里是噪声、在 v5 里是信号，区别只在于尺子。**

**设计对照组时的两个要点**：

1. 对照组必须在**同一次运行、同一份数据**里产生，不能拿另一次会话的重复性当噪声
   底 —— 那测的是别的东西（见 §9.9）。
2. 两个变体最好是**同一份源码 + 一个 monkeypatch**（v4/v5 都是把旧规则装回去），
   而不是两个 checkout。这样"对比夹带了别的改动"这种可能性从构造上就不存在。

## 9.2 夹心口径：单向会吃掉约 0.3% 的热漂移

**做法**：两个方向各测一遍，取几何平均。v4 的顺序是 `v3 → v4 → v4 → v3`，v5 是
`v4 → v5 → v5b → v4b`，**四趟都在同一会话内**（v5 是 14:28–15:35 之间跑完）。

| 轮次 | 单向（A 先跑） | 单向（B 先跑） | **夹心** |
|---|---|---|---|
| v4 对照组（69 点） | 0.9971× | 1.0003× | **0.9987×** |
| v5 对照组（24 点） | 0.9994× | 1.0017× | **1.0006×** |

**单向口径偏 0.1–0.3%，方向固定：后跑的那一组吃热漂移。** 夹心把 v4 压到
0.13%、v5 压到 0.06%。

**代价**：测量时间翻倍。**什么时候必须用**：当你要读的差异 < 1% 时。v3 那一轮
收益 geomean 11.7%、最大 84.8%，单向背靠背（相隔 62 秒、两组时钟窗口相同）就够
了 —— 但那一轮的时钟恰好被 DPM 钉死在 1400 MHz，cv ≤ 0.38%。v4 之后时钟开始在
1602–2150 MHz 浮动，cv 变成 0.08%–3.35%，**夹心从此是必须的**。

## 9.3 顺序：先修宿主开销，再扫 tile

**这是 v3 最重要的一条方法论结论，而且它解释了十几轮扫描为什么没找到东西。**

所有历史 tile 扫描都跑在 47 µs 派发还在的时候。gpt-oss fc2 @ `avg_m=512` 那时候
整整 103 µs 的调用里几乎全在等 CPU ——

> **两个在 GPU 上差 37% 的 tile，在计时器上是一模一样的。**

派发降到 3 µs 之后，同一批 tile 立刻分出 1.34×–1.42× 的差距（§8.3）。

**推广**：任何"被一个与被测量无关的固定成本盖住"的维度都测不出来。动手扫参数
之前先问：**这个点的 wall 里，我要动的那部分占多少？** `T_tile = F + n_phase × P`
（§8.6.2）就是用来回答这个问题的 —— 它正是靠"每波固定成本 F = 4.1–5.2 µs"把一个
只值 0.1–0.3 µs 的候选排到了线下。

## 9.4 compile-only ISA 门：一分钟省一轮 bench

**做法**：候选进 bench 之前先编译、只看 metadata 三个字段：

| 字段 | 判据 |
|---|---|
| `.vgpr_count` | 对着悬崖 `min(131072 / flat_workgroup_size, 1024)` 比 |
| `*spill_count`（vgpr / sgpr / scratch） | **> 0 直接判掉** |
| `group_segment_fixed_size` | LDS 预算；对着 `327680 / n` 判 WG/CU |

**实测效率**：v5 一轮门跑了 **75 个 PASS / 6 个 SPILL / 2 个非法**；其中"在固定
tile 尺寸下砍掉每 lane 累加器"这一臂 4 个候选**全部 spill（59 / 250 / 288 /
435）**，**一个都没送 bench** —— 不是"试了没用"，是代数上不存在。更早的一轮用同
一个门**判掉 3 个候选，共花 11 秒**。

**两个必须知道的陷阱**：

**① `flyc.compile()` 默认会真的 launch。** compile-only 必须显式设
`COMPILE_ONLY=1`。这不是效率问题 —— 见 §9.11 的第一条，这是把整张卡打挂的路径。
稳妥的做法是在脚本入口**硬性拒绝**在没有该环境变量时运行（v5 的三个 ISA 脚本
就是这么写的）。

**② `group_segment_fixed_size: 0` 不等于不用 LDS。** 用
`fx.SharedAllocator(static=False)` 时 LDS 是**动态的、大小在 launch 时给**，
metadata 里那一栏是 0，而实际用量是 278528 B。判 WG/CU 要自己按公式算，不能读
这一栏。

## 9.5 CUDA graph：作为优化无价值，作为 GPU-only 尺子很有用

**[实测]** 修完派发之后，**72/72 个点的 graph 回放都比真实 Python 调用更慢
（慢 0.6% – 5.4%）** —— graph 自身约 3–4 µs 的启动成本已经超过它能省下的那点宿主
开销。**作为优化手段，这条路是死的。**

**但它是一把很好的尺子**：回放时整个 Python wrapper 一行都不跑，只剩内核 + 一次
graph launch，所以 `e2e − graph` 就是**没有被 GPU 掩盖掉的那部分宿主开销**。
（因为 graph 自己有启动成本，这个数是真实 GPU 时间的**上界**。）

它当场纠正了一个判读错误：

| 判据 | 优化前 | 优化后 |
|---|---|---|
| 启发式（`µs/call < 3× 96 µs 地板` ⇒ host-bound） | 37 / 72 | 38 / 72 |
| **graph 实测：宿主占 > 5%** | **4 / 72** | **0 / 72** |
| **graph 实测：宿主占 > 2%** | **6 / 72** | **0 / 72** |

**37 个点里 31 个是误报。** 原因很直接：宿主的 96 µs 是**异步下发**的，与上一个
内核的执行重叠，只有超出 GPU 时间的那部分才暴露。优化前真正被拖住的 4 个点，
最大暴露量是 **26.2 µs**，不是 96 µs。

**可行性提前确认**：`torch.cuda.CUDAGraph` 在这套栈上 **144/144 点全部捕获成功，
零失败**。

## 9.6 归因阶梯：一次只动一个因素，剥不开就说剥不开

`tile_n=192` 那条改动**四件事同时变了**（tile 面积、warp tile、LDS/occupancy、
ragged），扫描分不开。v5 的做法是搭一个 15 臂的阶梯：**每一臂只动一个因素，其余
（面积 / acc / LDS / ragged / 波数 / WG-per-CU）按标注固定**，然后逐条报。

结果见 §8.5.3。这里只讲方法上的三点：

**① 好的臂长什么样。** 最干净的一臂是 `nb3 → nb4`：LDS 从 138240 推到 184320
（越过 163840 那条线），**tile / warp tile / acc / vgpr(232，ISA 实测) 一字不
差**，唯一变化是 2 WG/CU → 1 WG/CU。这样才能把 +15.5% 归给"第二个
workgroup"。

**② 还要有反向对照。** `16 波 × 1 WG` vs `8 波 × 2 WG`，**同一个 tile、同为 16
波/CU** —— 这一臂把"波数"和"独立 workgroup 数"分开了，否则两者永远同向变化。
同理，"4 波"的杠杆要靠 `4×1` 网格这个负对照才能确定它是"方形 warp tile"而不是
"波少"。

**③ 剥不开就如实说。** `ldsfree_regbound_256` 本来是"寄存器 vs LDS 谁是约束"的
判决实验，实测 0.8169×，**但它同时把 `nb3` 降成了 `nb2`**；而同一轮里
`128×192` 单独做 `nb3→nb2`（WG/CU 不变）也损失 0.8181×。两者几乎相等 ⇒ 这一臂
的损失可以被 `nb2` 单独解释完，**判决不成立**。报告里写的是"剥不开，如实说剥不
开"，而不是挑一个解释。

**④ 推断要逐条标注。** 上面那 +15.5% 的依据里有一环是"`nb` 本身近中性"，而那是
在**另一个 tile（256×256）**上实测的，没有在 `128×192` 上单独隔离。报告把这一条
明确标成**推断**而不是实测。

## 9.7 数据质量：不可信的那一批怎么处理

**[实测]** v5 的一份扫描文件里有一批测点**重复间摆动 20%–148%**（同一个点单次
读数在 586–1102 TF/s 之间）。怀疑与单进程内累积了 384 个已编译 kernel 有关，
**未确认**。

处理方式，三条都值得抄：

1. **标记，并写明它不进任何结论**。报告里那份 jsonl 被显式标注为不可靠，只用作
   **候选筛选**（相对排序），绝对值一个都不引用。
2. **筛出的候选全部在受控条件下重测**。重测口径：行内交错、固定重复数、极差
   门限。
3. **重测不一致就不采纳**。`160×192` 在筛选里读到 +5~+29%，受控重测里在 fc1 赢
   6.4%、在 fc2 输 1.4% —— **不一致，未采纳**，并且在报告里把"那批筛选数据本身
   不可信"写在结论旁边。

另一条相关的纪律：**汇总时只取重复间极差 < 5% 的干净点**（§8.5.1 那张 259 点的
表就是这么筛的），并把点数、min/max、负点数一起报出来，而不是只报 geomean。

### ⚠️ 单形状、单条件的一次读数，不足以判一个 < 1% 的效应

**这是本项目最贵的一次教训。** 一个候选（`256×256×128` 的 4 波 2×2 网格）在某轮
的候选表里被记成 **"实测 −0.6%，弃"** —— 那是**一个形状**（deepseek fc1，G=8，
`avg_m`=8192）上的**一次**对比，而且它只是那轮 `tile_k` 扫描的顺带项。

后来同一个 tile 的同一个翻转在 **47 个点**上读到 **+1.3% ~ +1.5%**，别的 tile 上
最高 **+5.3%**，池化 259 点 **+3.7%**。

**这不是"当时测错了"，是"当时的采样量不够判这个量级"。** 可操作的结论：

- 一个候选要么用**足够多的点**判（多形状 × 多 `avg_m` × 两个 pass），要么**只记
  录不结论**（写"单点读数 −0.6%，样本不足"，而不是"弃"）。
- 顺带项尤其危险：它不在那轮的主线上，没人会给它配对照组和重复数。
- 判负清单里的每一条都该带上**点数**。本篇 §9.12 第 9 条就是为这个。

## 9.8 隔离测量 ≠ 流水里的测量（本项目验证过三次）

**[实测]** 三次都是同一个形状：**编译门漂亮 / 微基准漂亮 / 算术上确实省了，端到
端为负。**

| 候选 | 隔离口径 | 端到端 |
|---|---|---|
| 宿主侧建 M-tile 索引表 | 56 µs vs 92 µs，**更便宜** | **−31%**（D2H 同步杀掉了调用间的重叠） |
| `inkernel_scan` | 编译门与默认路径**逐项相同**（464/0/0），5 个正确性套件 ALL PASS，算术上省 23.6 µs | **fwd −15.2% / dgrad −53.8%** |
| 一个转置读指令的微基准 | 读到"更快" | 与真实 GEMM 里的行为不符，**该微基准已作废** |

⇒ **编译门与微基准是必要条件，不是充分条件。** 它们的正确用法是**判负**
（spill > 0 就不用测了），而不是判正。任何"孤立看更便宜"的候选都必须在端到端口径
上再测一次。

`inkernel_scan` 那次还留下一个可复用的信号：坏点伴随 **cv 从 0.1–0.5% 飙到
11–46%**。**cv 突然变差本身就是一个诊断** —— 它说明这不是"多干一点活"，而是病态
行为（那次的推断是标量加载退化成带串行依赖的向量加载，**未做 ISA 确认**）。

## 9.9 跨会话比较：先核对时钟，否则整批数据会系统性偏移

**[实测] 这台机器出现过 DPM 退化态**：`pp_dpm_sclk` 的 level 1 被卡在
**1400 MHz**（健康值重启后读到 **2244–2248 MHz**，不同会话读数略有差异），空载
即 1400 MHz，**锁不到最高档**。后果是那一整轮的绝对数字系统性偏低。重启清除。

换算（同 72 点，重启前后）：

| 量 | geomean | 范围 |
|---|---|---|
| TF/s 之比 | **1.166×** | 0.969 – 1.337 |
| 负载 sclk 之比 | **1.304×** | 1.155 – 1.531 |
| **每时钟之比** | **0.894×** | — |

**那 1.166× 全部是 DPM 档位回来了，不是任何优化的功劳。** 而每时钟反而掉到
0.894×，因为时钟涨了 30% 而 HBM 没有 —— 访存受限的形状吃不到时钟。

**规则**：

- **跨会话比较绝对值之前必须核对 `sclk`**，并把逐点 sclk 记进结果表。
- 上一轮的 v3 做过一次干净的跨会话自检：同 72 点偏差**中位 −0.16%**、范围
  −3.53% … +0.50%、超出 ±2% 的 4/72 —— 之所以能复现，是因为**两次会话的 DPM
  档位相同（都卡在 1400 MHz）**。这是运气，不是方法。
- **同会话内的比值不依赖这一点**，这也是为什么交付表的前后对比一律同会话。
- 本仓库 [`06-pitfalls.md`](06-pitfalls.md) §6.4 的"跨 session 的数字和同 session
  的比值是两种主张"讲的是同一件事的另一面。

## 9.10 正确性与确定性怎么配合性能实验

性能实验会引入两类静默错误：**选了一个算错的 tile**，和**看起来变快其实是漏算**。

### 新几何必须另写正确性用例

**[实测]** 现成的 T1/T2/T3 打不到新分支 —— T3 的 `avg_m` 是 1163，在 1536 门槛
之下。所以每次动选型规则都另写专项用例，v4 写了 12 项、v5 写了 176 项，故意包含
**规则不该触发**的形状（`N=5000` 不是 192 的倍数、`N=2881` 奇数尾）来验证 ragged
路径仍然对。

### 判定口径要测的是几何，不是 shape

v5 改了判定方式，这一条值得抄：**不再用一个硬编码的 rel_err 区间**（那测的是
shape），而是要求**每个候选在同一份输入上与生产 tile 的 rel_err 之差 ≤ 1e-6**。
结果是 **176/176 PASS，`max |Δ vs 生产 tile| = 0.00e+00`**。

**为什么必须这么做**：筛选阶段出现过 `BN=224`、`BM=160` 这种既不整除输出宽度也
不整除 `avg_m` 却排第一的候选。**"因为悄悄漏算了 ragged 尾巴所以更快"的表现正是
这样。**

### 确定性 soak 的脚本陷阱

**[实测]** 现成的确定性脚本把**第 1 次调用**当参考。刚编译出来的 config 头 1–2
次可能返回损坏结果，于是参考本身是坏的、后面每一次都"不同"：

| 跑法 | 未改动的基线 | 优化版 |
|---|---|---|
| 原样（第 1 次当参考） | **报 8 个 PROBLEMS** | 报 3 个 |
| 加 3 次预热 | 1 个 | 0 个 |
| 参考同时留在设备上再比 | **0** | **0** |

**两边都是预热伪影。** 判据：如果**未改动的基线**也报问题，那问题在仪器里。
正式的 soak 口径是 10 个用例 × 3 pass × 200 次背靠背启动、**主机侧逐位比对且报
差异时再问一次设备**（避免把主机拷贝的抖动算到内核头上）；两个版本各 6000 次
启动、设备侧不一致 **0 / 12000**。

### 参考实现用 fp32，不用 fp64

**[实测]** 本机 device fp64 matmul **12 个 shape 错 11 个**。参考必须是 fp32，
判定在 host 侧。本仓库 [`06-pitfalls.md`](06-pitfalls.md) §6.3 记的是同一条。

另一个同类的仪器故障：**设备侧布尔规约会说谎**。有一个点报 `nan=True` 而 rel 正常
0.1409%；专门复跑 40 次，设备侧 `torch.isnan(out).any()` **0/40 为真**，主机侧同样
**0/40**。

## 9.11 工具与环境陷阱（会让你判断反向的那几个）

### ⚠️ 不要为省显存缩小算子而让 grid 仍按真实 M 算

**这条会把整张卡打挂。** `flyc.compile()` 默认真 launch（§9.4），加上"算子开小
而 grid 按真实 M 算"，会发出越界 workgroup。本机 `gpu_recovery` 在挂死时读到
**`0`（禁用）** —— 在 `gpu_recovery=0` 的机器上任何设备侧 fault 都是**永久挂
死**，没有 ring timeout、没有 queue reset，**只能整机重启**。

（重启后同一个节点读到 `-1`。所以这个值**不是稳定属性，要在会话开始时现读**。）

纪律：compile-only dump **一律按真实形状分配操作数**，一次都不要缩。

### ⚠️ gfx11+ 改了指令名 —— 按旧名 grep 会得到"全零"的假象

| 旧名（gfx9 时代） | gfx11+/gfx12+ |
|---|---|
| `ds_read_*` | **`ds_load_*`** |
| `ds_write_*` | **`ds_store_*`** |
| `s_waitcnt` | **`s_wait_loadcnt` / `s_wait_dscnt` / `s_wait_kmcnt` / `s_wait_tensorcnt`**（还有 `s_wait_alu` / `s_wait_xcnt`） |

**实际后果**：曾因此误判"我们的核不用 LDS"。生产配置 `256×256×128/b2` 的真实
计数是：

```
tensor_load_to_lds     4
tensor_store_from_lds  1
ds_load_b128         192      ← 按 ds_read_* 去 grep 会得到 0
ds_store_b128         32
```

三条自洽性检查都指向"用 LDS"：指令名；`s_wait_dscnt: 11`（没有 LDS 访问不会去等
DS 计数器）；静态条数与源码逐项对得上（每 K-tile `4×2+8×2=24` 条 × `K_WS=4` =
96，两个 body ⇒ 192 ✓）。

同类的第二个坑：**同步指令计数漏类会把比值算低**。少数了 `s_wait_alu`(70)、
`s_delay_alu`(34)、`s_wait_tensorcnt`(4)、`s_wait_xcnt`(1) 之后算出 0.098，正确
值是 **0.117**（文档字面口径）或 **0.523**（含 `s_wait_alu`+`s_delay_alu`）。
**两个口径都要报**，因为参考标尺用的是哪个口径通常没写。

### ⚠️ 磁盘上的历史 ISA dump 未必是当前内核的

43 个历史 dump 里有一半是旧内核的，特征是 `s_mul_i32 ...,3` + `s_load_b96`
（每 tile 3 宽表）。**引用一个 dump 前先确认它属于哪一版内核**，否则会拿一条已
过期的观测去推翻当前实现。

### 统计口径变了要回归验证

从 `mean-of-timeit` 换成 `median-of-repeats` 有可能**凭空制造出一个加速比**。
验证办法：用新统计方法重测**同一条 baseline**，看比值是不是 1.0000（实测 72 点
1.0000，区间 0.966–1.047）。

## 9.12 一页清单

开一轮性能实验之前：

1. **这轮要读的差异有多大？** < 1% ⇒ 必须夹心 + 对照组。
2. **对照组是什么？** 找出规则命中不了的那些点，它们的真值必须是 1.0000×。
3. **wall 里我要动的那部分占多少？** 被固定成本盖住的维度先修固定成本（§9.3）。
4. **候选能不能在编译期判掉？** `COMPILE_ONLY=1` + spill / vgpr / LDS 三个字段。
5. **grid 和操作数形状一致吗？** 不一致就会挂卡，且可能只能重启。
6. **新几何有专项正确性用例吗？** 包含"规则不该触发"的形状。
7. **参考是 fp32、判定在 host 吗？** 是否 burn 了前 3 次调用？
8. **`sclk` 记了吗？** 要跨会话比的话，DPM 档位核对了吗？
9. **每个数字旁边写了口径吗？** 点数、重复数、单向还是夹心、噪声底多少。
10. **这一批数据的重复间极差是多少？** 超过门限的点要么重测，要么标记为不进结论。
